# 融合方案是否替换默认模型

日期：2026-10-09。结论：亮光融合是减少误报的改进，但不是对原模型各方面都更优。已将其接入软件为可切换的候选模式；当前默认原模式保留。其 42 秒确认延迟和覆盖下降不符合直接替换为唯一常规方案的条件。

这里的“融合”是第三方模型按类别分工：候选提供 fire、原模型提供 smoke，经过原时序确认和风险模块。没有训练新的融合神经网络，不把模型选型包装成自主网络创新。

## 同一开发组的比较

30 段开发视频，共 28,611 帧；两类误提示均指确认状态在负标签上的活动片段。fire 覆盖分母为 7,317 个真值正标签帧；平均延迟按三方案共同检出的原有 8 个 fire 事件匹配，避免用不同事件集合比较平均值。

| 指标 | 原模型 | 之前 UAV fire + 原 smoke | 此次亮光 fire + 原 smoke |
|---|---:|---:|---:|
| fire 场景检出 | 8/13 | 9/13 | 9/13 |
| fire 确认误提示 | 3 段 | 3 段 | 0 段 |
| smoke 场景检出 / 确认误提示 | 9/11；1 段 | 9/11；1 段 | 9/11；1 段 |
| fire 正标签帧确认覆盖 | 72.1% | 76.4% | 55.5% |
| 同一批 8 个事件平均首次确认延迟 | 2.97 秒 | 1.07 秒 | 6.67 秒 |

之前 UAV 组合更适合继续评估常规检测替代：覆盖、延迟和事件检出较好，但保留车灯/反光误提示，双模型计算成本增加。亮光组合适合对误提示更敏感的场景继续研究，但当前不能通过“零误提示”掩盖持续检测变差。两者新增命中的事件也不同，不能认为 9/13 意味着命中了完全相同的事件。

之前 UAV 组合另有一次固定的 14 段内部留出检查；此次亮光方案只有开发检查，不能把前者留出结果移用给后者。原内部留出已曝光、训练重叠未排除；默认替换前应补充新来源验证，而不是反复使用同一留出挑参数。

## 接入方式与采用条件

新增软件模式只改变检测器来源，原 `core/detector.py`、时序、评价和标注保持不变。原模式继续支持原来的阈值设置；候选固定使用已经验证的 0.35，其他类别不会进入火情评分。候选缺失或权重 SHA256 不匹配时明确报错，不静默改用其他模型。

界面可随时在分析开始前切换；分析中锁定设置。命令行支持 `--model-profile brightlight`。结果保存两个分支的来源和阈值，方便对照、导出和后续追溯。

要把亮光融合提升为常规默认，需要同时处理：

1. 在新来源灯光、反光、红色物体负例上维持误提示收益；真实火焰靠近亮光/红色物体的正例也必须纳入。
2. 分析 `posVideo5.874` 约 42 秒确认延迟和长视频断检，不以放宽时序的方式未经验证地换回误报。
3. 验证实际软件、CPU/GPU、长视频与跨机器运行成本，明确可接受的延迟和漏报取舍。

本轮接入的实际运行与界面检查另见 `FUSION_RUNTIME_REPORT.md`。原始模型对照和具体误框见 `BRIGHTLIGHT_MODEL_REPORT.md`、`CLASS_ROUTING_VALIDATION_REPORT.md`。
